# Обновления SpaceWeb без постоянного копирования команд

Подготовлен ручной процесс GitHub Actions для существующего приложения
`forms.eduinterpain.ru` на VPS `194.226.99.172`.
Ветка настройки: `ops/manual-spaceweb-deploy`. Эта настройка не сливает PR справки №1,
не запускается при push/PR и сама по себе не меняет работающий сайт.
До согласования настройки и реальной проверки на VPS процесс нельзя считать готовым.

## Как будет выглядеть обычное обновление

- Пользователь описывает изменение здесь, ассистент меняет код и обновляет PR в GitHub.
- После тестов пользователь подтверждает выпуск конкретной версии.
- Ассистент запускает workflow для полного SHA коммита и подтверждает ожидающее
  задание защищённого окружения в рамках уже данного разрешения.
- GitHub Actions отправляет архив на VPS; больше не нужно копировать патчи в Терминал.
- VPS устанавливает зависимости новой версии в отдельном каталоге,
  переключает только приложение и проверяет `/health`, `/spravka` и защиту API.
- При ошибке запускается попытка вернуть предыдущую версию и проверить её здоровье.
  Отказ питания, диска или самого VPS может помешать автоматическому восстановлению.

Запуск использует `workflow_dispatch`. Для доступности ручного запуска workflow должен
находиться в основной ветке, поэтому добавление отдельного служебного PR в `main`
нужно явно согласовать.
[Документация GitHub](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

## Что создаётся один раз

- Отдельное окружение GitHub `spaceweb-production`, не старое Vercel `Production`.
- Допуск к этому окружению только из `main`, проверяющий `rkowalyov`,
  запрет обхода защиты администратором.
- Возможность владельцу подтвердить запуск, инициированный его же аккаунтом:
  иначе ассистент, использующий подключение владельца, не сможет завершить выпуск.
- Отдельная пара SSH-ключей. Приватный ключ сохраняется непосредственно через
  `gh secret set` в секрет окружения `SPACEWEB_SSH_KEY`, не в чат, репозиторий или логи.
- Публичный SSH host key VPS после получения с сервера через действующее доверенное
  подключение сохраняется в `SPACEWEB_KNOWN_HOSTS`; слепой `ssh-keyscan` не используется.
- На VPS создаётся новый пользователь `b24deploy` с заблокированным паролем.
  Его единственный ключ имеет forced command и `restrict`: произвольный shell,
  SFTP, SCP, туннели и интерактивный терминал через этот ключ не предоставляются.
- Root-owned шлюз `/usr/local/sbin/interpain-release` и узкое sudo-правило.
  Шлюз принимает только `check`, `deploy <40-символьный SHA>` и `rollback`.

Окружение может требовать подтверждение до доступа к секретам.
[Правила защиты окружений GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).

## Минимальный одноразовый ручной шаг

Прямой SSH из инструментов ассистента заблокирован, а локальный браузер Comet ранее
не подключился. Поэтому первый вход администратора на VPS полностью убрать нельзя
при текущем доступе. После согласования будет подготовлен комплект из установщика,
шлюза и публичного ключа, переданный на Mac.

Потребуется один раз перенести комплект и запустить установщик через существующий
root SSH из Терминала. Приватный ключ копировать или присылать не нужно.
Установщик не меняет файлы приложения, `.env`, Nginx, Docker или действующий SSH root.
Он не перезапускает приложение и SSH-сервис. В конце выводит только результат
настройки и публичный host key VPS.

При несовпадении ожидаемого сервиса, пользователя `www-data`, каталога приложения
или существующем конфликтующем deployment-пользователе установщик останавливается.
Если установка прервётся после начала изменений, повторный запуск не перезаписывает
конфликтующие объекты: нужно отдельно разобрать частичное состояние.

## Режимы ручного workflow

- `check` (режим по умолчанию): проверить SSH, состояние сервиса и три HTTP smoke-check.
  Не менять приложение, симлинки, Git или сервис.
- `deploy`: протестировать выбранный коммит на изолированном GitHub-hosted runner
  без deployment-секретов, затем отправить его runtime-архив через pinned SSH.
- `rollback`: переключить приложение на предыдущую записанную версию.
  Это изменение сайта и перезапуск, требующие разрешения, как и выпуск.

Установщик и `check` не являются разрешением выполнить `deploy` или `rollback`.
Первый выпуск и последующие версии согласуются отдельно.
Автор workflow также ограничен `rkowalyov`; задания не запускаются от чужих аккаунтов.
Никакого self-hosted runner на рабочем VPS не устанавливается.

## Размещение версий и сохранение рабочего состояния

Исходный каталог `/opt/interpain_b24forms` с Git-правками остаётся на месте.
Его `.env` не читается инструментами упаковки и не переносится в GitHub.
Сервис продолжает получать переменные из существующего EnvironmentFile.

При первом разрешённом выпуске:

- Новая версия создаётся в `/opt/interpain_b24forms-releases/<SHA>`.
- Временная сборка выполняет `npm ci --omit=dev --ignore-scripts` от `b24deploy`,
  не от root. Перед активацией файлы становятся root-owned и не доступны этим
  пользователям на запись.
- Создаётся `/opt/interpain_b24forms-current`, указывающий на выбранную версию.
- Добавляется только drop-in `30-spaceweb-releases.conf` сервиса
  `interpain-b24forms.service`: WorkingDirectory и ExecStart новой версии.
- Порт `3001`, пользователь `www-data`, существующий EnvironmentFile и Nginx
  не меняются. Docker на `3000` не затрагивается.
- Перезапускается только этот сервис, выполняются smoke-check.

Первый выпуск кратковременно прервёт обработку запросов приложением.
При последующих выпусках также есть перезапуск: это не zero-downtime.
Git в исходном каталоге не переключается, `pull/reset/clean` не выполняются.
Старые версии автоматически не удаляются.

## Что входит в архив

Только `server.js`, `package.json`, `package-lock.json`, корневые HTML и обычные файлы
в `api`, `lib`, `assets`, `scenarios`, плюс манифест SHA-256.
`.env`, существующий отслеживаемый `.tmp.env`, приватные ключи, `.git`, workflow,
установщик, тесты, документация и локальные зависимости в runtime-архив не входят.

Шлюз проверяет SHA, манифест, пути, число файлов и размер.
Архивные symlink/hardlink, устройства, повторные пути и выход из каталога запрещены.
Лимиты: 50 MiB сжатого архива, 200 MiB распакованных данных, 5000 файлов.

## Состояние проверки

Подготовлены тесты упаковки, исключения секретных файлов, ограничений команд,
проверки путей, манифеста и попытки восстановления после ошибки.
Локально прошли 16 тестов этой механики; `actionlint` не нашёл ошибок workflow.
Архив реальной версии справки `4d52653` собран без `.env` и dev-зависимостей.
Из распакованного архива приложение запущено локально: `/health`, `/spravka`,
`/event-register` вернули 200, API без пароля — 401.
Откат проверяется локально с подменёнными системными командами, не на живом VPS.
Реальные SSH, установка зависимостей на VPS, защита окружения и выпуск ещё должны
быть проверены после согласования и одноразовой настройки.
