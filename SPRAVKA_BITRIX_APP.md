# Подготовка интеграции справки с Битрикс24

Подготовлена отдельная ветка `feature/spravka-bitrix-entry` от `main` версии `8f31ce07a7f011b545f9e751b5a40fd6dcc60265`. Ветка опубликована и открыт [PR №6](https://github.com/rkowalyov/interpain_b24forms/pull/6), без слияния в `main`. Приложение в портале не создано, рабочий сервер не обновлён; подключение требует отдельного согласования.

## Что получит сотрудник

- **Вход из портала:** сотрудник открывает приложение «Справка по мероприятиям» в интерфейсе Битрикс24. Сервер проверяет его доступ и показывает прежнюю справку без запроса отдельного пароля.
- **Одинаковый отчёт:** все допущенные сотрудники видят общие данные через существующий серверный вебхук. Персональные CRM-права сотрудника не меняют подсчёты.
- **Резервный вход:** адрес `https://forms.eduinterpain.ru/spravka`, существующий логин и пароль остаются. Этот путь не зависит от настройки или доступности OAuth.
- **Выбор и копирование:** существующие чекбоксы, «Выбрать все», одна кнопка «Скопировать», порядок мероприятий и четыре строки подсчётов сохранены.

Серверное локальное приложение может открывать собственный интерфейс внутри iframe Битрикс24; при открытии портал передаёт авторизационные параметры текущего пользователя методом POST. Это не просто публичная ссылка на страницу справки. ([Документация серверного приложения](https://apidocs.bitrix24.ru/local-integrations/serverside-local-app-with-ui.html))

## Где управлять сотрудниками

Планируем использовать доступы установленного приложения: **Приложения → Маркетплейс → Ещё → Установленные приложения → меню приложения → Доступ**. В справке Битрикс24 этот путь описан для приложений Маркетплейса; наличие и точное расположение такой настройки для созданного локального приложения нужно подтвердить непосредственно в вашем портале перед включением интеграции. ([Настройка доступа к приложениям](https://helpdesk.bitrix24.ru/open/17398580/))

В списке выбираются конкретные сотрудники или подразделения; пустой список означает доступ всем, а не запрет всем. Поэтому включение серверного входа допускается только после проверки явно заполненного списка. ([Настройка доступа к приложениям](https://helpdesk.bitrix24.ru/open/17398580/))

Ограничение приложения не отнимает резервный вход у человека, который уже знает общий пароль. Это два независимых способа доступа, как и было согласовано.

## Безопасная последовательность подключения

### Подготовить приложение и сервер, не открывая справку через портал

- **Тип:** локальное серверное приложение с интерфейсом; не входящий вебхук и не статичная страница.
- **Название:** «Справка по мероприятиям».
- **Путь обработчика:** `https://forms.eduinterpain.ru/spravka/bitrix`.
- **Название пункта меню:** «Справка по мероприятиям». В этой версии используется обычный пункт приложения; отдельная регистрация виджета `LEFT_MENU` не выполняется.
- **Самостоятельное завершение установки:** опцию «Приложение само завершает установку» оставить выключенной. Наш обработчик не вызывает `BX24.installFinish`; незавершённое приложение не может получить сессию отчёта.

Серверное приложение и настройка самостоятельного завершения установки описаны в официальном руководстве. Регистрация специального виджета `LEFT_MENU` является отдельным механизмом и не входит в этот этап. ([Серверное приложение](https://apidocs.bitrix24.ru/local-integrations/serverside-local-app-with-ui.html), [Виджет главного меню](https://apidocs.bitrix24.ru/api-reference/widgets/left-menu.html))

Для чтения текущего пользователя достаточно наиболее узкого доступного scope `user_brief`; приложению не нужны права CRM, поскольку сам отчёт продолжает получать данные старым серверным вебхуком. Метод `user.current` поддерживает `user_brief`, `user_basic` и `user`, а `user.admin` относится к базовым методам. ([Версии scope пользователя](https://apidocs.bitrix24.ru/api-reference/user/user-scope.html), [Текущий пользователь](https://apidocs.bitrix24.ru/api-reference/user/user-current.html), [Проверка администратора](https://apidocs.bitrix24.ru/api-reference/common/users/user-admin.html))

В существующую конфигурацию сервиса потребуется добавить только следующие настройки, не меняя резервный пароль или вебхук:

| Переменная | Значение и назначение |
|---|---|
| `SPRAVKA_B24_CLIENT_ID` | Код созданного локального приложения, ожидаемое значение `app.info.CODE` |
| `SPRAVKA_B24_ENABLED` | Сначала `0`; только точное значение `1` включает выдачу сессий справки |
| `SPRAVKA_B24_STATE_DIR` | `/var/lib/interpain-spravka-bitrix`, постоянный закрытый каталог вне сайта и каталогов релизов |

Каталог состояния необходимо заранее подготовить для пользователя службы `www-data` с режимом `0700`. Запись `installation.json` создаётся приложением с режимом `0600`; в ней хранится секрет установки, поэтому файл нельзя добавлять в GitHub, публиковать, копировать в веб-каталог или присылать в чат.

Нынешний ограниченный SSH-доступ GitHub Actions умеет проверять связь и выпускать версии, но не предоставляет произвольную root-консоль. Подготовка постоянного каталога и новых переменных требует отдельной согласованной настройки; обычный выпуск сам по себе этого не делает.

### Закрепить установку и проверить права

- **Первое открытие:** выполняет администратор портала. Обработчик проверяет OAuth только на фиксированном домене `interpain.bitrix24.ru`, ожидаемый код приложения, ID текущего пользователя и результат `user.admin`.
- **Закрепление:** после этих проверок сервер создаёт запись с ID приложения, `member_id` и `APPLICATION_TOKEN`. Уже существующая запись не перезаписывается автоматически.
- **Выключенный вход:** при `SPRAVKA_B24_ENABLED=0` страница подтверждает подготовку приложения, но не выдаёт сессию и не загружает отчёт.
- **Список сотрудников:** администратор настраивает явные доступы приложения. До включения проверяем фактический экран прав вашего портала и согласовываем список.

Закрепление `APPLICATION_TOKEN` соответствует требованию проверять входящие параметры приложения, а не доверять одному `DOMAIN`, `Referer`, `USER_ID` или присланному адресу REST. В этой реализации первый секрет закрепляется только после отдельной серверной проверки администратора, а не от первого анонимного запроса. ([Проверка параметров приложения](https://apidocs.bitrix24.ru/local-integrations/serverside-local-app-with-ui.html))

### Включить после отдельного разрешения

- **Активация:** только после согласования установить `SPRAVKA_B24_ENABLED=1` и перезапустить службу согласованным способом.
- **Положительная проверка:** допущенный обычный сотрудник открывает приложение и видит справку без пароля.
- **Отрицательная проверка:** сотрудник вне списка не получает отчёт; затем проверяем отзыв доступа уже открытой сессии.
- **Резерв:** прежний пароль открывает прямую страницу независимо от настроек приложения.
- **Регрессия:** проверяем одинаковые подсчёты, выбор, копирование в реальном iframe, мобильный экран и действующую регистрацию на мероприятия.

`app.info` позволяет проверить код и состояние приложения; системная ошибка `user_access_error` означает, что администратор ограничил доступ к установленному приложению. Реальную работу этой проверки с вашим локальным приложением необходимо подтвердить после установки, а не считать проверенной по тестовым ответам. ([Метод app.info](https://apidocs.bitrix24.ru/api-reference/common/system/app-info.html))

## Как устроена защита

- **Проверка перед данными:** каждый запрос справки по сессии приложения заново вызывает `app.info` и `user.current` до чтения общего кэша отчёта. Решение о доступе отдельно не кэшируется.
- **Общая справка:** Basic и приложение используют один обработчик, один кэш и прежний способ подсчёта. Правильный резервный пароль проверяется до любых OAuth-запросов.
- **Короткая сессия:** после стартового POST сервер выдаёт браузеру случайный непрозрачный Bearer-токен. OAuth-токен не включается в HTML и не сохраняется сервером на диск; для сессии не нужны cookies, `localStorage` и `sessionStorage`.
- **Срок:** не более 50 минут и не дольше переданного положительного `AUTH_EXPIRES`. Обновление OAuth через refresh token не реализовано; после истечения или перезапуска сервера нужно заново открыть приложение из портала.
- **Выход:** браузер очищает отчёт и отправляет запрос удаления серверной сессии. При недоступной сети невозможно подтвердить доставку запроса выхода; серверная сессия всё равно ограничена сроком и повторной проверкой доступа.
- **Встраивание:** только ответ `/spravka/bitrix` разрешает iframe с родителем `https://interpain.bitrix24.ru`. Защитные заголовки обычной страницы и регистрации не ослабляются.
- **Ошибки:** секреты и исходные сообщения OAuth не выводятся в ответы или новые журналы обработчика. Конфигурацию журналирования reverse proxy и самого портала нужно проверить отдельно при подключении.
- **Ротация установки:** несовпадение кода, ID приложения, `member_id` или секрета приводит к отказу. После переустановки нужна отдельная согласованная процедура перепривязки, не автоматическая замена доверенного секрета.
- **Управление резервом:** отключение приложения или отозванный доступ не отключают существующий пароль.

## Что проверено

- **Node.js:** 34 теста прошли, включая 11 новых тестов интеграции, расширенную HTTP-проверку маршрутов и прежние тесты расчёта, фильтрации, копирования и авторизации.
- **Механизм выпуска:** 18 Python-тестов прошли; сам механизм выпуска в этой ветке не изменяется.
- **Негативные сценарии:** подмена портала и приложения, неверный секрет установки, неадминистратор при первом закреплении, незавершённая установка, выключенная интеграция, истечение сессии, отзыв доступа, смена пользователя и недоступность OAuth.
- **Реальные HTTP-маршруты локального приложения:** прямой вход, отдельные iframe-заголовки, POST из портала при ограниченном `ALLOWED_ORIGINS`, безопасная ошибка разбора тела и GET-переход на резервный вход.
- **Chromium с синтетическими ответами:** автоматический вход, непрозрачная сессия вместо OAuth в HTML, выбор одного/всех мероприятий, фактическое копирование в буфер, обновление с сохранением выбора, правила, выход, неверный пароль и резервный Basic-вход. Удаление серверной сессии приводит при следующем обновлении к 401, очистке данных и возврату формы пароля; ошибка 503 при первом входе не выдаётся за сохранённую предыдущую справку.
- **Встраивание:** проверен cross-origin iframe с тестовым родителем на доверенном origin портала, без cookies и без атрибута `allow="clipboard-write"`; копирование сработало.
- **Экран:** desktop 1360 px и mobile 375 px, без горизонтального переполнения; ошибок выполнения страницы не выявлено.

Все OAuth-проверки пока выполнены на тестовых ответах, а не на реальных токенах вашего портала. Создание приложения, подтверждение экрана доступов, живой отзыв прав, настройка сервера и производственный выпуск остаются следующим этапом после разрешения.
